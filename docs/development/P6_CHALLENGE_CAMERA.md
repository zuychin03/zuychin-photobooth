# Challenge camera

The challenge photo chooser now offers an explicit camera flow for each assigned source position, including sparse positions. `ChallengeCamera` reuses `useCamera`, `CameraPreview`, the existing dropdown and `runCaptureSequence`. Opening the panel does not request permission. Start camera requests it; loading, denied, unavailable, retry and close states remain visible. The timer defaults to three seconds, with five and ten seconds available. The countdown is static, with no flash or shutter sound. Mirroring applies to both the complete-frame preview and captured original.

A captured JPEG is reviewed locally before Use this photo prepares the existing account-scoped upload record and atomically saves its original through the P2 project repository. Only then is it selected. Neither capture nor selection uploads bytes or submits the contribution. Retake discards the current unselected preview; Keep local copy offers the reviewed JPEG independently. Closing discards the unselected preview. The established Upload photo and Confirm submission actions remain separate. Other challenge actions and photo selection are disabled while the camera panel is open; a frozen submission cannot open it.

`createChallengePhotoCapture` validates camera readiness and dimensions before allocation, captures unfiltered native pixels, verifies encoded JPEG header dimensions, and caps each image at 10 MiB, 4096 pixels per side and 12 megapixels. The production singleton permits only one native capture/encode allocation at a time. Its ten-second deadline or cancellation rejects the caller promptly but retains that slot until the underlying native operation settles. A stuck encoder can therefore make subsequent capture unavailable; it cannot accumulate another owned capture canvas. File selection remains available after closing the panel. Successfully allocated canvases are reduced to 1 × 1 after encoding or failure. Native encoder internals and browser camera buffers are not a hard memory sandbox.

The component retains one reviewed File and one object URL. Retake, close and unmount revoke the URL. Capture completion stops tracks before review; close, account-driven unmount and external disabling also stop them. The existing CameraController generation fence stops a permission result arriving after teardown. Cancellation is checked before local upload preparation and after its asynchronous return, so a late result cannot select a photo under a stale account. Local preparation interrupted after its journal write may leave a prepared recovery record, but makes no remote-deletion or remote-upload claim.

`createChallengeCameraOriginals` uses one local account-scoped project named Challenge camera originals, with ID `challenge-<challenge UUID>`. Media IDs equal stable upload asset IDs. This private single-person backup uses role A internally and retains the exact source index; it does not rewrite the challenge participant role. Its normal 24-file, 64-MiB and 48-MiPixel project inventory limits include older accepted camera originals. Retakes retain prior originals rather than replacing their bytes. Quota, CAS or unsupported-project failures keep the reviewed File available for download and retry. Retrying the same reviewed File reuses its prepared upload identity. Project metadata and media commit together; the initial manifest has revision zero.

After remount, selecting a pending upload with a saved original exposes Use saved camera original. The action loads from the exact account scope and verifies MIME, dimensions, length and SHA-256 against that upload record before allowing explicit upload. Other accounts cannot discover these originals. Verified cloud assets still use server discovery. Local Projects provides normal backup/export/delete affordances; no automatic original eviction or separate blob database is introduced. Browser storage remains best effort.

Account changes close the helper through the existing scope lifecycle. Concurrent close calls retain the same in-flight drain until it settles. The sign-out remove-local-copies project prerequisite now waits for scoped writers before editor draining and project deletion; independent cleanup branches remain independent. Successful sign-out with keep-copies leaves originals scoped to that account.
