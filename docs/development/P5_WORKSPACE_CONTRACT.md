# P5 room workspace storage

Recorded 23/09/2026. `openRoomWorkspaceStore({scope, roomId, sessionId, selfId})` owns a scoped metadata connection and a connection to the existing project repository. It contains no credentials, cookies, invitation secrets or media copies. Metadata retains member IDs/roles, host ID, roster revision, accepted recipe and frozen capture identity. Completed and previous draft projects remain ordinary local projects.

## Adapter API

- `loadDraft(roster: RoomState): Promise<RoomDraft>` selects or creates a draft for one exact admitted roster revision. It supports one to four members; a collaborative recipe requires at least two. New drafts select their layout and mode by the highest admitted role: A only uses a solo strip, B uses the duo layout, C uses trio and D uses quad. This preserves role gaps after removal and includes all four people; quad starts with three required shots. Existing drafts and captured rounds are not silently rewritten. The deterministic draft ID includes a digest of scope, room/session/self and roster revision, within the project ID bound.
- `saveRecipe(commit, optionalMedia): Promise<RoomDraft>` persists a validated initial recipe or next ordered commit. Hashes, member ownership, project context, source availability and revision progression are checked. The optional map supplies new declared PNG decoration bytes. Missing files fail explicitly.
- `prepareRound(capture, recipe, optionalMedia): Promise<RoomRound>` creates the actual project at `capture.captureId` before readiness is acknowledged. It freezes participants, original capture hash, shot IDs and delivery profile. It checks complete byte/pixel reservation including decorations against the current project ceilings. The project starts without old photos.
- `saveFrame({capture, role, shotIndex, blob}): Promise<string>` verifies committed capture identity, all frozen acknowledgements, member/role/slot, byte/MIME/pixel bounds, native image decoding and SHA-256. Its return value is the capture project ID, only after the source and project manifest transaction completes. The controller must persist the local original before returning from `captureShot`; the receiver must await this method before acknowledging a frame.
- `loadRound(captureId): Promise<RoomRound | null>` recovers the exact scoped round independently of the current roster. The stored `capture` is a frozen local checkpoint, not fresh authority. The engine must still consult the room server before transport or capture actions.
- `loadSavedFrame(captureId, role, shotIndex): Promise<Blob | null>` reads an existing frozen slot after reload without creating a source or shutter claim. It verifies role/member/media identity, exact project snapshot, declared bytes/MIME, native decoding and the frozen profile. Missing rounds or empty slots return null; damaged media is refused. The controller exposes resending only the current participant's own originals. The transport compares the original staging manifest SHA-256 before refilling an interrupted transfer and freshly authorises delivery; a local Blob read grants no room authority.
- `updateRoundRecipe(captureId, commit, optionalMedia): Promise<RoomRound>` applies ordered collaborative finishing without changing original source bytes, source mappings, required capture count or initial capture hash. `recipe.recipeHash` is the latest finishing hash; `initialRecipeHash` and `capture.recipeHash` retain the capture identity. The controller serialises draft save, round update and only then host broadcast.
- `acceptHostSnapshot(commit, optionalCaptureId, optionalMedia)` returns `{draft, round}` and is reserved for explicit reconnect acceptance after retaining a local fork. It validates the complete hash/ownership/context but permits a host revision gap. Ordinary saves remain strictly ordered. The controller must retain this explicit mode when retrying an interrupted acceptance.
- `close(): Promise<void>` immediately fences new work and success responses, drains existing work, then closes owned connections. A transaction already in flight may finish durably before close resolves. Global sign-out/project switching must await this boundary; no new frame starts after closure.

`RoomDraft`, `RoomRound`, `RoomWorkspaceStore` and `RoomWorkspaceError` are exported. The core factory accepts injected metadata/project dependencies for fault tests. Normal browser callers use the open function.

## Durability and recovery

Each frame uses the real project repository's atomic Blob-plus-manifest transaction, immutable media identities and expected-revision comparison. IDs such as `room-B-1` are deterministic inside the capture project. An exact retry verifies the stored bytes and returns the same project without another revision. Different bytes for an existing slot are rejected. Out-of-order frame delivery retains null earlier slots. Concurrent stale writers cannot replace each other's project revisions; a conflict requires explicit reload/recovery.

Workspace metadata and projects use separate IndexedDB databases, so a recipe change is not a cross-database atomic transaction. Before changing a project, the workspace durably reserves a pending checkpoint containing the exact target manifest, recipe and base revision. A retry completes only if the actual project is still at the expected base revision, or exactly equals the already committed target. An interrupted metadata acknowledgement can therefore finish after reload without applying the recipe twice. A divergent project, missing source, unknown/future manifest or damaged identity stops recovery and preserves the existing data. Pending new decorations require their bytes to be supplied again if the project transaction never committed.

Earlier roster drafts and frozen round participants are retained; removing a member from the live room does not rewrite captured originals. Current server membership remains a separate requirement for transmitting any further data. A local fork may be preserved using the public repository duplicate operation before explicitly accepting a different host recipe. This store never silently overwrites an out-of-order host snapshot.

The metadata database is `photobooth-room-workspaces-v2`, version two. The additive upgrade adds per-scope generation fences. Blocked/late opens time out, version changes close connections and writes compare metadata versions and scope generation within one transaction. Workspace operations hold an exact-scope Web Lock across metadata/project work, so account cleanup cannot interleave between those databases. Browsers without Web Locks cannot start this workspace persistence path. Capacity is 128 metadata records globally and 192 KiB per checkpoint, including any pending manifest. Browser eviction and physical storage failure remain outside this guarantee.

Authenticated room state supplies `expiresAt`; older records without it remain unknown, never assumed expired from timestamps. My projects provides explicit inspection and per-room confirmation to clear only expired, non-pending metadata in visible device/account scopes. It preserves active/unknown-expiry checkpoints, transfer journals and all saved projects. Account removal is a separate explicit action: after confirmed sign-out, scope closers synchronously fence controllers, queues, workspaces and journals, then drain them before cleanup acquires the scope lock. Cleanup atomically increments each room database's scope generation and removes only that account's checkpoint, transfer and shutter-marker keys. Old connections cannot recreate those records. Project/template removal follows this boundary. Keeping copies closes account writers but retains the data.

## Evidence

Twelve focused tests cover initial role-complete layouts including roster gaps, immutable idempotent frames, out-of-order slots, finishing versus capture hashes, prior-roster retention, interrupted acknowledgement recovery, divergent-write refusal, explicit host snapshot acceptance, concurrent project CAS, close fencing, damaged references, reopened saved-original reads and identity/profile denial. These use injected storage and image inspection to force otherwise difficult failure boundaries.

`runRoomWorkspaceProbe()` in `lib/rtc/workspace-probe.ts` uses uniquely named disposable metadata/project/transfer databases and a synthetic PNG. In addition to its original six checks, it interrupts outgoing staging after the first chunk, closes both workspace and journal, reloads the original from the actual project repository and refills the original transfer UUID without duplicate media or changed bytes. It cleans only its own databases and never uses a camera, real account or hosted service. The seventh recovery check awaits a new native execution. Native quota abort and transaction rollback are also covered by the earlier P2 repository probe. Cross-device/network timing and phone acceptance remain separate gates.

Root observed all six workspace checks passing in desktop Chrome on 23/09/2026 (Australia/Sydney). `runRoomCleanupProbe()` adds native close-before-delete, exact-account Blob/metadata removal, untouched-scope reopen and expired-only housekeeping checks. It uses disposable databases, not a real sign-out. Two Node lifecycle tests verify synchronous exact-account fencing and complete drain even when one closer fails. Native cleanup execution and concurrent-tab integration are recorded by root separately.
