# Durable activity foundation

Source-level tranche, 23/09/2026. `006_v2_activity.sql` follows existing 001–005 migrations and does not replace their lifecycle, retention, finalisation or challenge functions. No hosted migration, public HTTP route, timeline UI, ritual delivery or recap renderer is activated by this work. The typed service adapter requires `PB_MEMORIES_ENABLED=true`, a valid service configuration, fresh authenticated identity and capability version 1. Missing configuration fails closed.

## Source identity and visibility

Additive source triggers record accepted legacy strip saves and project **photo** originals when they first become verified ready. PNG decoration finalisation does not count as a memory. The new source timestamp marker is generated by the trigger, ignores supplied insert values and preserves its old value on update. Existing direct authenticated strip updates cannot write the column. Immutable strip UUID tombstones and retained project asset identities prevent a deleted identifier from creating a new contribution. Source markers remain after detail compaction, so repeated updates/backfills do not increment totals again.

Strip occurrence means the existing immutable saved-at instant. New project activity means the server-observed first verified-at instant; an already-ready legacy asset backfill explicitly uses `legacy_created_at`, not invented capture time. The activity row never contains a caption, image path, email, signed URL, provider identifier or decoded media. It stores the original source scope ID without a cascading foreign key to a couple/project. Source purge/delete updates availability and leaves participation counts intact. Photo discovery remains in the existing authorised media stores, independently of activity detail compaction.

Shared detail requires membership in the **exact original** couple, or current accepted project membership for both the actor and original author. A later partner does not inherit an earlier couple's activity. Project detail additionally invokes the existing challenge representation gate. An accepted project owner cannot see another person's unrevealed protected original through activity. Read-time checks mean unpairing, project deletion, membership revocation and challenge access changes take effect without a copied permission snapshot.

After scope loss, a subject retains only their own activity ID, occurrence/provenance, `access_lost` state and personally authored annotation. Source IDs, scope IDs and other members' identities are absent. Other former members receive no row. Chapter/occasion labels are personal and never appear in another member's projection. These records are not permission to resolve an image: every eventual preview/export must use the current source resolver.

Availability is `available | archive_pending | archived | expired | deleted | unknown | access_lost`. A strip is archived only when its source is purged and it has a persisted verified archive marker/reference. A purged historical reference without that verification remains `unknown`, not confirmed expired or readable. This does not promise that a later provider request succeeds. An expired/deleted entry is activity only. Relay-completion/session/reveal events are deliberately absent from this tranche; counting those as well as their originals would need an explicit product definition and durable replay identity. No inferred session totals are exposed.

## Finite growth without blocking saves

Per subject, retain at most 2,000 unannotated detailed rows and 500 annotated rows. A chapter or occasion pins a row. A source commit may compact the oldest unannotated detail, but never removes an authored label, deletes media, changes retention or rejects an otherwise accepted photo merely because the detail limit is reached. Removing the last annotation makes the row eligible for compaction; the mutation itself retains the edited row while trimming other eligible detail. Annotation attempts above 500 return capacity and preserve the existing data. Personal chapters are capped at 100, with an 80-code-point trimmed title; one optional chapter and one 80-code-point occasion label are supported per activity in this tranche.

Separate own-participation counters use fixed **UTC** calendar-month buckets for 1970–2199, at most 2,760 rows plus one explicit outside-calendar bucket per account. Counts increment once at source recording and never decrement on media deletion or detail compaction. The output declares `timezone:"UTC"` and `basis:"own_source_records"`. It must not be relabelled as a user-selected IANA civil year, a session count or a count of available photos. Local-year photo selection remains a separate future query over currently accessible sources. Counters contain no scope/member/caption information, so retained own totals cannot revive former group details. Account deletion cascades these new metadata tables.

The detail cap is global per subject, not 2,000 new rows every year. This intentionally narrows the earlier integration-document sketch to a finite bound. Aggregate counts can therefore exceed the listed detail count. UI copy must label that grouping and must still allow all retained media to be found through its existing authorised listing. The schema has no automatic background delete of personal labels or photographs.

## RPC and adapter surface

All new tables have RLS enabled with no direct grants, including service-role table access. Internal record/projection/trigger helpers are not directly executable by clients or service role. Public entrypoints are service-only with fixed `search_path`; their actor comes from fresh `getUser` in `createActivityStore`, not a request-supplied owner ID.

`pb_memory_capabilities()` reports version 1 and exact bounds. `pb_memory_list(actor,afterUUID,limit)` uses UUID keyset pagination, default 20/max 50, and sanitised projections. It lists current visible detail, not a snapshot; membership or compaction can change later pages. `pb_memory_summary(actor,year)` returns only that actor's 12 UTC monthly totals and the outside-calendar total. `pb_memory_chapters_list` returns at most 100 personal chapters.

`pb_memory_chapter_put(actor,id,expectedRevision,title)` creates with expected revision -1 and revision 0; updates require exact revision and increment once. `pb_memory_annotate` uses the same exact-revision rule, requires ownership of both the activity and any chapter, and increments once. `pb_memory_chapter_delete` requires exact revision and an empty chapter, so it cannot silently strip labels from activities. Ambiguous mutation acknowledgements require a fresh list before retrying with a new revision; the service must not blindly repeat an edit or create a new UUID to bypass a conflict.

The TypeScript adapter exposes `list`, `summary`, `chapters`, `putChapter`, `annotate` and `deleteChapter`, returns allowlisted typed values and rejects mismatched IDs/revisions. Each public operation charges the existing actor-bound read/write rate gate internally. A future HTTP wrapper must not double-charge it. Reads and responses are bounded; eventual routes still need the established same-origin/Bearer/no-store checks. No source-record insertion endpoint exists.

`pb_memory_backfill(limit)` is a separate service maintenance operation, 1–100 records per call (default 25), locking batches with `SKIP LOCKED`. It touches only unrecorded existing strips or already-ready photo assets. It neither fabricates deleted history nor downloads media. Reruns use protected source markers and cannot resurrect compacted detail or recount an original. No automatic full-table backfill runs in the migration.

The [bounded activation runner](P6_ACTIVITY_BACKFILL.md) defaults to a zero-network dry-run and requires explicit `--apply` for any RPCs. It resumes from these server markers, without a weaker local cursor or automatic retries.

## Local verification and remaining integration

`tests/activity.test.ts` covers strict source/minimal projections, private annotation removal, page/cursor validation, explicit UTC summary semantics, bounded CAS inputs, actor binding, rate ordering, response identity/revision checks and configuration/schema failure. The isolated `database/tests/run-activity.mjs` harness creates and destroys its own `pb_v2_activity_*` PostgreSQL database. It installs the real additive migrations over the fixture legacy schema, exercises existing populated rows and reruns, compacts over 2,000 historical originals while preserving a pinned label and exact counts, rejects marker forgery/reset, checks concurrent CAS/annotation/chapter ceilings, preserves counts through purge/delete, checks exact-couple/re-pair isolation and invokes real project finalisation before checking protected-source omission/revocation.

The PostgreSQL harness has mock Supabase auth and Storage metadata. It establishes actual SQL triggers, grants, transactions and concurrency, not hosted Supabase Storage bytes, signed-link behaviour, Cloudinary availability, provider activation or browser UI. HTTP/UI integration, yearly photo selection, relay/session event semantics and ritual delivery remain separate work. The migration must be reviewed and consolidated in order before an operator applies it; do not replay an older source migration over later protection gates.
