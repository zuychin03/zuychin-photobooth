# Event browser transport and guest recovery

Source foundation, 23/09/2026. No event feature flag, hosted database or provider was activated. The browser transport uses the existing 005/016 routes, the additive 017 host surface and the independently implemented provider signing endpoints. UI, fragment takeover, cookie behaviour on real devices and a complete kiosk are separate acceptance gates.

## Browser clients

`createEventHostClient({appOrigin,identity,accessToken,fetch?,timeoutMs?})` snapshots `{ownerId,epoch}`. It exposes `ownerId`, `assertActive`, `close`, `capabilities`, `create(eventId,input)`, `dashboard(eventId,{after?,limit?})`, `manage(eventId,action,body)`, `issue(eventId,{requestId,kind,expiresAt,rotate})`, `revokeToken(eventId,token)`, `list({after?,limit?})`, `settings(eventId)` and `saveSettings(eventId,{requestId,expectedRevision,settings})`. Each asynchronous method accepts an optional final AbortSignal. Token refresh and every response are fenced against the original account epoch. Missing hostVersion defaults to zero for base-route compatibility; 017-only calls fail unavailable on older servers. Settings retries may return a newer current revision, not a historical response.

`createEventGuestClient({appOrigin,eventId,identity,storageOrigin?,fetch?,timeoutMs?})` snapshots either null or `{eventId,guestId,epoch}`. A null client may explicitly redeem an invite or inspect a cookie session; the caller must then create a new client with the returned guest identity. A scoped client cannot redeem a replacement invite. Methods are `redeem(inviteToken,nonce)`, `session`, `reserve({requestId,submissionId,consent})`, `consent(submissionId,consent)`, `finalise(submissionId)`, `exchangeReceipt(submissionId,token)`, `readReceipt(submissionId)`, `mintUpload(submissionId)`, `upload(submissionId,blob,grant)`, `media(submissionId)` and `download(submissionId)`.

Private JSON uses same-origin cookies, no-store and redirect refusal. Host bearer tokens are obtained only for authenticated calls, never capabilities or Storage. Inputs and outputs have exact allowlists; response JSON is capped at 64 KiB/4096 chunks. Default request timeout is 10 seconds (maximum 45 seconds), with caller abort and closed-client fences even when a test transport ignores AbortSignal. Errors contain bounded codes and Retry-After 1–60, never arbitrary server messages. A timeout does not prove that a dispatched mutation rolled back.

Guest mutation bodies include expectedGuestId. The server compares this with the verified captured request cookie before using that same token for the mutation. This closes a cross-tab contribution-cookie replacement race. It is a mismatch fence, not caller-provided authority. Receipt operations independently bind the exact submission. Cookies remain one contribution slot and one receipt slot; returning a different receipt explicitly replaces that cookie.

Signed URLs are ephemeral return values only. The client validates the independently configured Storage origin, fixed bucket/path, only one token query field, no credentials/fragment, exact submission, expiry and no-overwrite. Uploads send raw image bytes with `x-upsert:false` and omit app credentials/referrers. HTTP 400 is uncertain, not success. A 409 permits finalisation verification but does not claim that the bytes match. Staging images are at most 2,000,000 bytes and pass the bounded still-image header parser before transfer; the server worker performs actual decode and derivative verification.

Receipt download fetches at most 2,000,000 JPEG bytes and rechecks current media authority before publishing a Blob. It validates container header, dimensions and MIME, but the current server descriptor contains no digest or exact dimensions. It therefore makes no end-to-end hash claim. Native rendering remains the consuming UI's responsibility. No signed URL is written to a journal or generic cache.

## Device storage decision

`openEventGuestJournal({identity,databaseName?,indexedDB?,now?})` stores immutable event/guest/request/submission IDs, an explicit three-destination consent snapshot and original image SHA-256/MIME/bytes/dimensions. By default it stores **no original bytes**. `prepare({requestId,submissionId,consent,blob,keepOnDevice,eventExpiresAt})` retains the Blob only when `keepOnDevice:true` reflects the person's explicit choice. No invite, nonce, receipt token, contribution token, signed URL or host credential is persisted. All three consent values must be supplied; publication never defaults to true.

The whole device queue is limited to eight records, 16,000,000 retained bytes and eight open event/guest scopes. Each original is at most 2,000,000 bytes, 4096 pixels per edge and 12 million pixels. One prepare/hash operation runs per handle. Expiry is the earlier of 24 hours and event expiry; expired records and media are purged before that scope is exposed. This is a temporary recovery queue, not a kept personal photo library. UI must explain expiry and offer explicit local export while the original remains available. Bytes cannot be erased while the browser is closed; purge runs on the next open. Separately downloaded personal files are outside this queue and are not removed. Capacity failure preserves uncertain entries instead of silently evicting them.

Records use revision CAS and immutable frozen identifiers/consent/image descriptors. `list/get/update/remove/purgeExpired/close` never start network work. `reserveEventGuestRecord` commits the reserving marker before calling the server. `uploadEventGuestRecord` requires an already-reserved record, so the UI can present its private receipt before bytes leave. It is an explicit foreground action: it matches retained or reselected bytes, persists uploading before mint/PUT, preserves uncertain PUTs for exact retries and records finalisation separately from ready. Already-finalising status recovery does not demand the original again. Only a ready receipt clears the retained local Blob. `refreshEventGuestRecord` replays the original reservation identity to recover that exact receipt slot without storing its secret. Changes to publication consent do not rewrite the original reservation fingerprint.

If a response or local acknowledgement is lost, the record retains the same request/submission IDs. The next explicit action can retry or refresh; there is no interval, service-worker queue, background sync or automatic network retry. A closed/expired/revoked event may refuse retry. Local bytes can still be exported until the separately promised queue expiry, but no new server identity is generated to bypass refusal.

## Exact cleanup and kiosk boundary

`clearEventGuestJournal(eventId,guestId,options?)` closes matching local writers, deletes only that exact scope and its records atomically, and invalidates already-open independent-context handles through a stored random generation. Reopening creates a new generation; stale handles cannot resurrect, delete or read its contents. Other event/guest handles remain valid. The caller closes its client and changes its UI epoch before explicit session replacement; the cleanup function does not clear cookies or revoke server grants. A late cookie-clear response could race with a newer redemption, so uncoordinated server-cookie clearing is deliberately absent.

This is a personal-device guest recovery queue, **not** the approved operator-only kiosk queue. The latter requires a separate event-device upload capability and coordinated turnover of camera/mic, object URLs, UI and receipt secrets. Those capabilities/flows do not yet exist. Never carry a previous guest's receipt secret into an operator queue or expose a previous queue to the next guest.

## Verification

Focused Node tests exercise response/identity/timeout bounds, account refresh races, guest replacement denial, signed origin/path/overwrite rejection, uncertain 400 and 409 handling, real encoded JPEG final access revocation, original-byte matching, immutable consent, pre-network local persistence, lost reservation acknowledgement and interrupted-upload retry without new IDs.

`runEventGuestJournalProbe()` in `lib/events/guest-journal-probe.ts` is development-only and uses a uniquely named disposable IndexedDB database plus a locally generated PNG. It exercises default no-media persistence, opt-in exact reopen, immutable retry, revision races, whole-device capacity, exact cleanup, accountless session epoch changes and expiry. A dedicated module worker verifies that cleanup fences a separate JavaScript registry while another guest remains writable. Worker termination, canvas release and database deletion run in finally. Native execution is pending until the root browser rehearsal; these source probes are not evidence of a passed browser run.
