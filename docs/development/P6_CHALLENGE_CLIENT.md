# P6 challenge browser client

`createChallengeClient({appOrigin,identity,accessToken,fetch?})` binds one signed-in account and identity epoch. It supports capabilities, create, view, manage (accept/decline/open/cancel/withdraw), submit, proposePartial, partial, consentPartial and commitPartial. All calls accept a final optional AbortSignal. The caller supplies stable challenge, partial and submission request IDs; the client does not invent replacement IDs or automatically retry mutations after an uncertain response.

The only network destination is the exact same-origin `/api/challenges` POST endpoint. Calls use a fresh bearer token, omitted cookies, no redirects, no cache, a 10-second deadline, the shared 64 KiB request and 96 KiB response limits, and at most 4096 response chunks. Abort and account checks bracket token acquisition, fetch, each stream read and completion. Closing aborts active calls and clears transient consistency records. There is no token, signed URL, recipe or consent persistence in this module.

Response parsers use the shared frozen-template validator and source-assignment derivation. They check exact response IDs, unique member IDs/roles, declared source ownership/indexes, valid hashes, dates, bounded arrays and unique visible asset IDs. Only allowlisted fields survive. A create result must reproduce the requested project, design, roster, policy and expiry. A bounded 64-entry in-memory record detects frozen-context changes across observed responses; this is a consistency check, not permission or an offline source of truth. Legacy unsupported challenge/partial results remain explicit and mutations cannot report them as success.

Partial proposals must return the exact contributor set. Consent and commit responses must match the exact supplied digest, while a commit must return revealed with access intact. The client never manufactures consent, assumes a reveal from progress counts, or downloads a concealed source. Visible source IDs are solely those returned by the authorised server projection. A consumer must use the cloud client's fresh asset resolver for every original read. Partial reveals can legitimately expose a subset while the main challenge remains open; the browser does not override the server's independent representation gates.

Recipe/reveal/partial hashes are format-checked and bound to observed context. The browser does not reimplement PostgreSQL's canonical JSON hashing or claim those hashes establish authenticity. Server authentication and the authoritative SQL state remain required. No discovery, UI, provider configuration or hosted activation is added here.

Focused tests use injected HTTP responses for operation payloads, projection sanitisation, malformed ownership/source mappings, frozen-context changes, exact partial consent, legacy rows, wrong response IDs, account switches, cancellation, deadlines, stream limits and sanitised errors. They do not establish hosted Supabase or cross-device behaviour.
