# P6 memory and ritual integration contract

Read-only implementation handoff, 23/09/2026. This applies approved V2_PLAN T7 and its retention requirement: chapters, occasion labels, gentle rituals and a recap made only from retained, accessible photographs. It does not introduce another vault, scheduler, media service or permission model. The contracts below are the next bounded implementation tranche, not completed functionality.

## Current evidence and reusable code

`app/timeline/page.tsx` calls `lib/couple.ts:listStrips`, whose query excludes `purged=true`, fetches every matching row and signs every Storage path. The page derives streak/week counts from that result. Consequently, a photograph leaving the active vault can disappear from those counts. Its weekly recap loads every selected image concurrently, exports with `lib/recap.ts`, then automatically calls `saveStrip(...layoutId:"recap")`. That implementation is unsuitable for a year of originals or for an export-only annual recap.

`pb_strips` already has immutable owner/created_at, nullable historical couple ID, kept/purged/archive fields and P1 lifecycle protection. `pb_strip_quota_ledger` and `pb_media_jobs` preserve accounting and cleanup provenance independently of row deletion. `pb_discover_retention`, `pb_enqueue_strip_operation`, the fenced media job mutation/completion RPCs, `lib/server/media-worker.ts` and `media-store.ts` remain authoritative for archiving/deletion. Retention uses the configured database zone, preserves migration grace and does not release quota until confirmed cleanup. A Cloudinary reference or `kept=true` alone is not proof of a completed, readable archive.

`pb_photo_dates`, `lib/photo-dates.ts` and `lib/server/reminders.ts` implement the existing reminder feature. The current worker processes five dates per pass under `pb_acquire_job_lease("reminders",...)`, renews its 900-second lease, records email or per-subscription push delivery, then updates the next scheduled instant. `pb_reminder_deliveries` survives date deletion and keys checkpoints by date ID, scheduled instant and channel. However, `nextOccurrence` advances JavaScript process-local dates, and the table has no immutable civil anchor, IANA zone or revision. The timeline offers deletion, not pause/resume. Neither existing month-end behaviour nor current process timezone is an acceptable T7 schedule contract.

`lib/memories/ritual-schedule.ts` already provides pure, bounded, versioned recurrence with fixed anchor, explicit zone, clamp/skip, gap and fold policies. Its tests cover Sydney and Lord Howe transitions, month ends and leap days. It is not wired to the database or worker. `004_v2_memories.sql` currently implements frozen challenges and partial reveals; `pb_memory_activity`, chapter and occasion records are not yet present. The private project resolver and challenge protection gates already prevent generic membership from exposing withheld sources. Reuse those gates; never query protected originals directly for a recap.

## Durable activity, chapters and occasions

Complete the planned memory tranche of `004_v2_memories.sql` with `pb_memory_activity`, `pb_memory_chapters` and a small bounded activity-label relation. Activity is a source-derived record, not an arbitrary client assertion of a photograph or contribution. Use a unique `(source_kind,source_id,subject_id,event_kind)` key, an immutable occurrence instant, its provenance, the original source scope identity, a subject/owner identity, and a bounded state projection. Do not store signed URLs, Storage paths, provider credentials, thumbnails or concealed captions in activity.

Source kinds initially cover legacy strip saves, completed relay participation and verified project/challenge contributions. Creation must be attached transactionally to the authoritative commit, with exact replay idempotent. Candidate hooks are an additive strip insert trigger, existing relay completion guard and `pb_project_finish_finalisation` / `pb_challenge_submit` or reveal RPCs. Decide one product event per source rather than counting upload, finalisation and reveal as three memories. Source deletion, purge and access loss update availability without deleting the participation event. A before-delete hook snapshots only the required minimum while the source identity still exists. Existing P1 cleanup jobs and quota tombstones are evidence for reconciliation, not a new public activity feed.

Backfill only rows with verifiable provenance, in keyset batches of at most 100 with a durable cursor and idempotent keys. Existing strip `created_at` means saved-at; label it as such. It must not become a fabricated capture date. A local project can provide its immutable capturedAt/captureTimeZone only when the server accepts an explicit, bounded metadata contract; display that as client-reported capture provenance, not server-observed capture. Do not reconstruct missing years from current thumbnails, generate dates for absent records, or claim a complete history where the deployment has none.

Activity visibility is separate from photo visibility. For legacy activity, share only while the exact original couple exists and the actor is a member of that couple. `unpair()` deletes `pb_couples`, which currently sets strip couple IDs null and cascades relays/photo dates; durable activity must not cascade with that deletion. An owner retains their own minimal activity after unpairing. Another participant retains only their independently recorded participation, without the former partner's private captions or media descriptors. A newly paired partner must not inherit historical T7 activity through `pb_are_paired(owner,actor)`. This does not silently rewrite legacy strip reader policies.

Project activity requires current accepted membership in the exact project for shared details, and challenge-specific access for concealed representations. Invited/revoked users receive no shared activity details. Owners can retain a personal, minimal participation record after losing a project, but not other members' names, recipes, captions or asset identifiers. Project ownership must not override a challenge gate. Every thumbnail/read request repeats current source authorisation; a prior activity response is not a read grant.

Chapters are personal organisation first: owner ID, title, optional inclusive calendar-date range plus explicit display zone, revision and timestamps. Occasion labels are plain text attached by the activity subject, not edits to capture timestamps. Sharing a source does not share private chapter labels. Keep editing and deleting a label/chapter separate from deleting activity or photographs. A bounded server mutation uses expected revision and returns conflict on stale edits.

Routine conservative bounds for implementation: 100 chapters per account, 80 Unicode characters per chapter/occasion label, eight labels per activity, 2 KiB total public activity metadata, 50 activity entries per page, 12 year-summary buckets per response and 25 items per maintenance batch. To keep activity growth finite without stopping an existing legacy save, retain at most 2,000 detailed activity entries per account/calendar year and compact overflow into exact daily counters with provenance and scope-level visibility. Preserve counts independently of media and label grouped entries honestly; never silently evict photographs or user-authored chapter labels. Compaction must not retain former-member details or merge independent scopes. Test this policy explicitly before adoption; it is an implementation limit, not an approved promise of complete unlimited history. Existing retained sources remain discoverable through their authorised media listing even when activity is grouped.

## Honest availability and annual recap

Return availability as a closed union: `available`, `archive_pending`, `archived`, `expired`, `deleted`, `access_lost`, `unknown`. These are source-derived states. `available` permits a fresh resolver attempt; `archived` requires a persisted verified archive reference and a currently authorised read path; neither guarantees that a later network request succeeds. Pending/failed archive jobs preserve the original and say that the archive is pending. Expired/deleted entries can contribute to activity counts but never to the image selection. Unknown historical metadata must stay unknown.

Add a paginated annual activity/list query with year and explicit display zone, computed as a civil-year interval rather than 365 elapsed days. Selection contains only currently accessible retained sources. List the number of activity records separately from the number of usable photographs: for example, “24 memories recorded, 8 photographs available”. No missing-image placeholder should imply an expired photograph is recoverable. An account/scope change aborts preparation, clears previews and releases decoded canvases and object URLs.

Extend the existing recap renderer and export flow with an explicit annual mode, not another composition engine. A conservative first export selects at most 12 photos, decodes sequentially, reduces each to a bounded 640-pixel thumbnail, releases the full original immediately and limits the output to the existing 4096-edge/12-megapixel still-image bounds. Preflight output geometry and use the existing bounded image decoder; do not call the current unbounded `Promise.all(loadImage(...))` on annual sources. Re-resolve access before each fetch; a denied/deleted source is removed from the pending selection with an explicit message, not silently replaced. Snapshot the selected IDs/dates and the export label; rendering must not change capture timestamps or claim every month is represented.

Default annual output is a local download, with a clear selection preview. Saving a generated recap to the couple vault is a separate explicit action through `saveStrip` and existing P1 upload/quota handling. The existing allowance remains one recap per ISO week; T7 does not bypass that quota with a new layout label. Saving to a project similarly uses the current bounded project reservation/finalisation path. Neither export nor activity preservation changes media retention, grants Cloudinary archiving, or reserves new provider capacity automatically.

There is currently no private legacy-archive read endpoint in this repository's `app/api` tree. Add a bounded, actor-verified legacy source resolver in the existing media route family, reusing the P1 archive identity/verification rules and existing Cloudinary adapter. Do not reuse `cloudinary_url` as public authority or infer another repository's Gallery access. Project originals continue through `/api/projects` read/download and the challenge gate. Provider-native archive read behaviour needs its own activation evidence.

## Extend photo dates into gentle rituals

Extend `pb_photo_dates` rather than introducing a second scheduling table. Add nullable legacy-compatible fields for schedule version, immutable anchor date/wall time, IANA zone, explicit recurrence policies, schedule revision, paused state and the next occurrence's cycle/UTC instant. Preserve `scheduled_at` as the indexed next due instant and preserve creator/couple identity. The initial public cadence remains once/weekly/monthly/yearly. One-offs keep their exact instant; recurring dates use the existing pure schedule module. Do not expose daily recurrence merely because the primitive supports it.

Fence rollback compatibility at the data boundary: versioned ritual rows keep legacy `active=false` and use a separate `ritual_enabled` field plus a partial due index. Otherwise an older deployed reminder worker can select a paused/new-zone row and send before its incompatible completion update is rejected. The upgraded worker handles legacy active rows separately and claims versioned rows through the new RPC only. Converting a legacy row atomically clears legacy active, sets the versioned fields and increments its revision.

Old rows do not contain enough information to infer their original timezone. Preserve their existing scheduled instant and legacy behaviour until their creator explicitly confirms an upgrade, showing the first occurrence in the chosen zone. Do not bulk interpret all old dates as Sydney or rewrite them earlier. New schedules require an explicit zone; preselect Australia/Sydney in the UI only as an editable default, and show the resulting local and UTC instants before saving. Travel does not change a saved zone.

Version-one UI defaults can be month-end clamp, gap shift-forward and fold later, with clear confirmation of any adjusted date. Persist these decisions, not just the next UTC result. Resume computes one future occurrence from the original anchor and current server instant; it does not send a backlog. A deliberate schedule/timezone edit increments generation/revision and recomputes the next occurrence without changing previous deliveries. Pausing is reversible and retains the reminder; deleting is a separate action. Use gentle count/history copy, with no broken-streak or penalty messaging.

For couple reminders, both recipients must still belong to the exact original couple and have enabled their channel. Unpairing or recipient revocation stops future delivery. Add recipient opt-out without allowing one person's preference to impersonate the other's consent. Personal/project ritual expansion is not required for the first T7 tranche; retain the existing couple scheduling context until an explicit accepted-project contract is needed. Cap new non-deleted photo dates at 20 per couple, with a 100-character title and existing per-actor write rate gate. Existing rows above the cap remain readable, pausable and deletable.

Enforce the date cap and actor/couple binding under the couple row lock on every insertion path, including the existing direct `createPhotoDate` insert. Restrict versioned schedule/generation columns to the new actor-bound service RPCs; an old direct mutation must not re-enable a versioned row in the legacy worker or forge its occurrence cursor. Preserve the legacy route only for genuinely legacy rows during transition.

## Delivery, pause races and idempotency

Keep `/api/reminders`, its cron authentication and current provider adapters. Extend `DueReminder`, `ReminderAdapter.due/complete/record` and `productionAdapter` to use service-only claim/fence/finish RPCs rather than direct table selection followed by a detached update. Claim at most five occurrences. Bind a lease to date ID, schedule revision, occurrence cycle/UTC instant and recipient set; check active/unpaused/current couple and channel opt-in immediately before each provider request and again on completion. Pause/unpair must invalidate queued claims. An already-sent provider message cannot be recalled, which needs honest UI copy and a pause-versus-send race test.

Extend `pb_reminder_deliveries` additively with revision/generation and recipient identity. Existing `email` means one historical group send; it cannot be treated as evidence that every future recipient was separately delivered. New delivery keys must include date ID, schedule revision, occurrence instant, recipient ID and channel/subscription ID. Send email per recipient, avoiding disclosure of the other recipient's address. Preserve historical checkpoint rows and the existing RPC for legacy work while adding a versioned recording entrypoint for new schedules.

Use one deterministic provider idempotency key per exact occurrence/recipient/channel. A sent-but-unrecorded response remains uncertain; retain it and retry according to the provider's documented idempotency window rather than claim exactly-once delivery. Push topic collapse is useful but is not an exactly-once guarantee. Keep per-subscription checkpoints and removal on provider 404/410. Use a five-attempt occurrence ceiling and explicit failed status; lease expiry/failed database acknowledgement must not advance the schedule. After terminal failure, show delivery trouble and schedule the next future occurrence only through an explicit reconciliation rule, never an unlimited retry loop. The current global 900-second lease coordinates runs but does not replace per-occurrence fencing.

Bound provider calls at ten seconds, delivery concurrency at two and due work at five occurrences per pass. Existing subscription lookup allows at most 20 targets; retain or tighten that bound. Do not log addresses, endpoint capabilities or reminder body text in worker errors. Durable per-channel checkpoints may be compacted only after the occurrence can no longer be retried: preserve a completed/terminal occurrence tombstone, advance the authoritative cursor, and make old generations permanently ineligible before removing detailed delivery rows. A concrete first limit is 100 terminal occurrence records per date, compacting older outcomes into month-level delivered/failed counts. No cap may make an uncertain occurrence sendable again.

## Migration, HTTP and UI order

1. Add the activity/chapters/ritual additions to the tracked memory migration as rerunnable additive statements, after P1 and project/challenge prerequisites. Existing installations need the corresponding forward upgrade, never a replay of an older 002 function that overwrites 004 protection gates. Preserve current `pb_challenge_capabilities` version 2/recipeVersion 1 and `pb_project_capabilities` apiVersion/finalisationVersion markers. Add a separate `pb_memory_capabilities` reporting activity, ritual and recap versions; missing versions disable only the new surfaces. Root later consolidates reviewed SQL into setup in dependency order.
2. Deny direct access to new tables and expose narrow service-only RPCs with fixed search_path. Bind HTTP identity through fresh `getUser`, not request owner IDs. Add bounded operations under one memory endpoint for list/year summary, chapter/occasion mutation, ritual list/create/edit/pause/resume/delete and permitted source resolution. Reuse same-origin checks, no-store responses and existing durable read/write actor rate buckets. Clients maintain account/epoch and AbortSignal fences. Do not make media maintenance depend on a browser request.
3. Wire durable source hooks and limited reconciliation before switching timeline counts. Keep legacy retention and Gallery-compatible columns intact. Add actor-scoped metadata deletion/export semantics independently of source-photo deletion. The existing sign-out remove-local-copies flow must clear any new local memory cache; preferably avoid durable browser caching of shared activity in this tranche.
4. Update the existing timeline with year navigation, chapter/occasion controls, honest photo-availability labels, bounded recap selection and a photo-date pause/resume/timezone editor. Reuse the existing warm-neutral design and Dropdown. Include missing schema, empty history, unpaired, revoked source, failed reminder, pending archive, offline and account-switch states. Keep private cloud projects separate from legacy couple inheritance.
5. Upgrade the current reminder worker behind capability checks; do not activate a second scheduler. Local SQL/HTTP/native fixtures can prove core transitions before any hosted service is enabled. The deployment timezone, provider configuration and hosted migration remain explicit operator actions.

## Required validation and actual blockers

Locally implementable next: schema/RPCs with empty and populated reruns; source replay/backfill tests; media purge preserves activity; exact historical couple isolation and re-pair tests; challenge representations omitted until permitted; pause/unpair/claim/send/finish races; revision/idempotency concurrency; failed-checkpoint recovery; Sydney/Lord Howe/month-end recurrence integration; annual count-versus-photo honesty; bounded renderer cancellation and account-change disposal; full timeline/reminder/recap UI states. Existing pure recurrence tests do not establish these integrations.

Current implementation gaps are the absent activity/ritual schema, authorised legacy archive resolver, bounded annual renderer and revised reminder worker. They can be developed and exercised locally. Historical deleted photographs and unsaved capture metadata cannot be reconstructed; the product must explicitly show incomplete history. Production retention timezone has to be deliberately configured, and real email/push/Cloudinary/Storage delivery, permissions, token expiry and provider idempotency remain external activation evidence. Phone testing is user-deferred and remains required for device capability/performance promises, not a reason to stop these local T7 foundations.
