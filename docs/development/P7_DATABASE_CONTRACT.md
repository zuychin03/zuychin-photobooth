# P7 event database foundation

Recorded 23/09/2026. This is the source-level event foundation in migration `005_v2_events.sql`, `lib/events/contract.ts` and `lib/server/event-store.ts`. It does not complete P7. No event route, upload endpoint, UI, image worker, export worker or hosted resource is activated. `PB_EVENTS_ENABLED` remains false; the consolidated setup is unchanged.

## Authority and isolation

The migration creates the eight planned event tables plus `pb_event_configuration` and `pb_event_jobs`. Every table has RLS enabled and direct privileges revoked from anonymous, authenticated and service roles. Only named RPCs are exposed to the service role. Private image staging and delivery buckets are declared when the Supabase bucket catalogue exists; a restrictive policy denies direct anonymous/authenticated access to both event buckets, including when another permissive policy exists. The capability probe requires both buckets to be private with the exact two-million-byte limit and image MIME allowlist.

Guest tokens are SHA-256 hashes, never raw secrets. Contribution, one-submission receipt, gallery and display are independent kinds. Every check binds the event, kind, expiry and revocation; receipt checks additionally bind exactly one submission. A revoked included contributor prevents future delivery reads and finalisation. Invites are separate from established sessions: rotating invites does not revoke existing guests. New redemption requires an open event within its contribution window and the event's guest ceiling.

Owner and moderator calls take a trusted actor UUID. The SQL verifies active event membership, with owner-only budget/window, invite, delegation and event-deletion operations. A moderator must accept an invitation while authenticated and can approve/hide/reject publication or remove an individual submission. There is no ownership transfer. The TypeScript adapter accepts owner calls only with a frozen actor object created by `verifyEventActor(auth.getUser())`, held in a module-local WeakMap for at most sixty seconds. The future route must supply the request-bound Supabase user client, never a service-role client or a body-provided user ID. SQL deliberately exposes no authenticated RPC taking an arbitrary actor ID.

## Limits and budget partition

The deployment allocation starts at zero. A service operator must explicitly configure an event-specific byte ceiling. Event creation allocates its entire configured maximum, at most 250,000,000 bytes, under the configuration row lock. Event budgets cannot collectively exceed that allocation; resize/configuration changes take the same lock. Expired/deleted events release the deployment allocation only after every staging and derivative charge reaches zero. Expired events cannot be revived after that release.

This ceiling is an operator-assigned partition, not a measurement of provider capacity. It must be distinct from the new project-scope allocation, legacy vault storage, other Supabase consumers and required operating headroom. Separate event/project configuration tables cannot detect an operator assigning the same provider allowance twice. Hosted capacity and egress observations remain activation requirements.

Per-event ceilings are 25 guest identities and 100 accepted or pending-cleanup contributions, subject to bytes. A reservation pessimistically holds 2,000,000 staging bytes plus 2,100,000 delivery/thumbnail bytes. Sixty concurrent full reservations fit the maximum event allocation; sixty-one do not. Count/bytes are checked under the event row lock, including retries and concurrent reservations. Creation stores an immutable canonical fingerprint (timestamps as epoch instants); the same event UUID with changed creation input conflicts even after later event edits. A unique event/guest/request key plus immutable request fingerprint preserves reservation idempotency. Logical failure/removal never frees physical bytes or its contribution slot without cleanup evidence. The slot remains charged until both staging and derivative holds reach zero.

Reservation creates the private receipt before upload. Each included contributor has an independent grant row, initially false except the submitter's supplied choices. Every contributor must use their own contribution capability to grant submission permission before upload authorisation; finalisation and each publication destination recheck all included grants. This is an event-consent foundation, not authorisation to copy unrevealed challenges or other participants' source projects. P8 still needs that separate source-scope transfer protocol.

## Upload issuance and finalisation

Logical reservations last ten minutes. The `authoriseUpload` RPC records a generation (at most eight), a mint deadline at most sixty seconds away, an authorisation deadline two hours after that mint deadline, and cleanup eligibility five minutes later. This happens before a future worker asks Storage to mint a token. The worker must refuse minting after `mintBefore` and verify the provider's actual expiry does not exceed `authorisationUntil`. A lost mint response remains charged. Reissuing does not add a new count/path; it extends the held expiry before another token can exist. Overwrite is always false and the path is exactly `<event UUID>/<submission UUID>/source` in the image staging bucket.

This intentionally reserves up to 126 minutes from authorisation setup rather than assuming the external mint occurred instantaneously. No external token has been issued or tested by this implementation. The clip staging bucket and media paths remain deferred until their later media gates.

Delivery states are reserved, uploading, finalising, ready, failed, expired and deleted. Gallery/wall states are independent. The private receipt reports a passed logical deadline as expired even before a sweep runs. Pausing or closing blocks new reservations but permits previously accepted work until the earlier of its logical expiry or closure plus ten minutes. Event deletion, individual removal or contributor revocation blocks finalisation immediately. Expiry is stored explicitly with IANA timezone; after first acceptance, expiry cannot be shortened or start/timezone rewritten. An owner extension revalidates allocation and extends promised expiry; early close does not alter it. The future create UI must apply the approved seven-day contribution and thirty-day retention defaults and show their concrete instants before consent.

Finalisation is queued and idempotent. Guest enqueue returns only the exact receipt state, never the internal worker lease or checkpoint. Completion requires an active lease, current submission/consent/lifecycle checks, trusted decoder/verification checkpoints, allowed MIME, dimensions no greater than 4096 per edge/12 MiPixels, a SHA-256 value, and actual Storage metadata sizes within 2,000,000 delivery plus 100,000 thumbnail bytes. Only then does the submission become ready and unused derivative headroom release. Gallery/wall become awaiting approval only where every contributor consented. Approval never overrides refusal. Withdrawing one destination preserves the other and the private receipt; withdrawing submission queues complete removal.

Read access returns only a fixed delivery path and a maximum signed-read lifetime of five minutes, shortened at promised expiry. It does not mint a URL. Receipt, gallery and wall authorisation are independent. Existing signed reads/downloads cannot be recalled; actual mint/cache/revocation behaviour is still unverified.

## RPC and job contract

The adapter exposes capabilities, create/manage/dashboard, redeem/reserve/authoriseUpload, consent/receipt/readAccess, enqueueFinalise and claim/checkpoint/finish/sweep. Their corresponding SQL names use the `pb_event_` prefix. Dashboard pagination is at most 25 records. Typed responses reject changed bucket/path, inconsistent limits, excess signed-read lifetime and malformed jobs. SQL errors map to bounded public codes without raw database detail.

`pb_event_jobs` has finalise, delete_delivery and delete_staging kinds. Claims use row locks, `SKIP LOCKED` and submission-scoped locking to prevent concurrent kinds, including within one batch. At most ten jobs are claimed, each with a fresh 120-second lease and eight-attempt ceiling. Checkpoints renew only the exact live token; finalisation checkpoints also recheck revocation and deadline. Cleanup cannot run while a finaliser is queued, running or retrying. Expired leases and terminal finalisation failures retain inspectable state and cleanup provenance.

Deletion completion requires a trusted `deleted=true` checkpoint and absence of the exact Storage metadata objects. Staging additionally requires its persisted cleanup deadline. Passing time alone does not free bytes. Sweeps process at most 25 submissions across 25 events and rotate the event maintenance cursor so older blocked events do not permanently starve later ones. Confirmed deletion is idempotent; completed leases cannot be reused.

A Storage metadata trigger requires derivative writes to include the exact live finalisation job UUID and lease in `user_metadata.eventJobId` and `user_metadata.eventLease`. It locks the event/job/submission, rechecks all contributor consent and deadlines, and rejects stale generations, ready or terminal submissions, and writes after capacity release. These fields are service-only worker metadata, not guest authority. The future worker must send them through the installed Storage upload metadata option. Actual hosted mapping to `storage.objects.user_metadata` and provider rollback after a trigger rejection remain activation checks; the trigger fails closed when metadata is missing. Database rejection alone does not prove that a provider left no physical orphan. The worker must use bounded provider deadlines, fresh lease checks before effects, deterministic non-overwriting paths, and provider reconciliation before claiming deletion. Uncertain physical writes retain accounting until confirmed cleanup. Failed cleanup remains charged and needs operator repair; a public failed-job retry UI is not implemented here.

## Local evidence and remaining integration

`node database/tests/run-events.mjs` creates a uniquely named database in the task-owned local PostgreSQL 16 container, applies the legacy baseline plus migrations 001/003/005, reruns 005 empty and populated, and drops only its own database in `finally`. It uses actual PostgreSQL grants, RLS, row/advisory locks and separate concurrent connections. Auth and Storage catalogues/object metadata are fixtures.

Observed locally:

- Direct anonymous/authenticated/service table reads denied; foreign owner and moderator escalation denied.
- Receipt-per-session/cross-event isolation, separate token kinds, invite rotation preserving existing sessions and independent contributor grant withdrawal.
- Immutable promised retention, receipt-before-upload, pessimistic mint/cleanup timestamps and refused finalisation without evidence.
- Eight competing claimers receive one lease; wrong/stale lease checks reject updates. Delivery writes with a previous lease are rejected after re-claim; writes after ready/removal/confirmed cleanup are rejected, and an unrelated permissive Storage policy does not expose the bucket.
- Twelve concurrent reservations admit exactly the three remaining reservations, with the expected byte total.
- Eight concurrent event creations admit exactly one remaining deployment allocation.
- Closure grace, immediate revoke, retained delivery charge until confirmed deletion, retained live-token staging charge, deletion confirmation after simulated expiry, and one-time deployment allocation release.

Seven focused TypeScript tests cover fail-closed configuration/schema, verified actor provenance, exact reservation/receipt identity, upload permission fields, private read bounds, bounded errors and receipt-only guest finalisation responses. Full TypeScript and focused lint were run during implementation; the final integration result is reported by the parent task.

Not yet implemented or proven: event API cookies/fragment redemption/rate limiting; host look/template and caption persistence; guest/host UI and local upload recovery; actual Supabase Storage upload/mint/lifetime/cache behaviour; server codec dependency and image worker; owner-only resumable ZIP exports/manifests; reminder delivery; multi-participant source-scope consent; deployed policies, provider budget and device rehearsal. These are remaining approved P7/P8 work, not claims established by the foundation tests. No hosted write or legacy quota change occurred.
