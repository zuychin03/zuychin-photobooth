# P6 challenge discovery

Forward migration `007_v2_challenge_discovery.sql` depends on 002 and 004. Migration 006 is the independent activity follow-up. Discovery does not activate either cloud or challenge feature flag and does not grant client table access.

`ChallengeClient.list(projectId, after?, limit?, signal?)` sends `POST /api/challenges` with `operation: "list"`, an exact project UUID and optional exclusive UUID cursor. The default and maximum page size are 20. The HTTP boundary validates the envelope and applies the authenticated project read rate before opening the challenge store. The service RPC binds its verified actor in `pb_challenge_list(p_actor,p_project,p_after,p_limit)`.

The result is `{ version: 1, challenges, nextCursor }`. Each summary has exactly `id`, `projectId`, `status`, `policy`, `membership`, `createdAt`, `expiresAt` and `unsupported`. No caption, title, design, recipe hash, assignment, submission state, participant identity or asset reference appears. Opening a row fetches the existing authorised challenge view. Unsupported legacy recipes remain identifiable as unavailable history without inventing a design.

Only the caller's frozen challenge memberships are discoverable. Accepted project members can see their own accepted, invited, declined or withdrawn challenge history. A still-invited project member sees only challenges that explicitly invite that actor. Generic project ownership or membership grants no visibility into challenges without a frozen participant row. Missing membership, revoked membership and deleted projects are denied. Every page rechecks these conditions; no cursor carries authority. Invite acceptance and original resolution retain their existing separate authorisation rules.

Rows sort by immutable UUID, using `id > after` and fetching at most 21 rows to establish the next page. The cursor is the last returned UUID only when another row exists. Inserts before an already-used cursor appear on refresh rather than being silently duplicated during pagination. Draft/open challenges whose deadline has passed are projected as expired without needing a scheduler mutation.

Core capabilities stay at version 2 and recipeVersion 1. Migration 007 adds `discoveryVersion: 1` and `listMaximum: 20`. The service store requires those markers only for list, while core operations remain compatible with 004. The browser list parser separately requires the version-1 list envelope and validates exact project IDs, ordering, uniqueness, cursor progression and the page bound. Missing or incompatible discovery SQL returns unavailable; it never silently falls back to a broader query.

Local checks: `tests/challenge-discovery.test.ts` exercises malformed/cross-project/concealed projections, stale cursors, the service actor binding, HTTP validation and read-rate ordering, browser requests and compatibility with core-only SQL. `database/tests/run-challenge-discovery.mjs` creates and removes a disposable database in the task-owned local PostgreSQL container, applies 007 twice, and checks real service-only permissions, invitations, non-participant isolation, revocation, deletion, expiry, unsupported history and 24-row pagination at multiple page sizes. No hosted SQL or provider requests are part of this tranche.
