# P7 event HTTP and capability transport

Source-only integration, 23/09/2026. Requires reviewed migration 005 followed by additive `016_v2_event_transport.sql`. The independent transport marker fails closed on older deployments; existing worker/store methods remain compatible with 005. `PB_EVENTS_ENABLED` remains false. No hosted schema or provider operation was performed. Image upload/download, gallery/display browsing, export workers and UI are separate tranches.

## Configuration and request boundary

Production additionally requires `PB_EVENT_TRANSPORT_SECRET` (32–4096 non-whitespace characters, securely random), `PB_EVENT_TRUSTED_IP_HEADER`, canonical HTTPS `PB_PUBLIC_ORIGIN`, service configuration and the public Supabase anonymous key for host verification. The deployment must strip/overwrite the selected trusted IP header; never select an attacker-controlled forwarded header. An absent, comma-separated or malformed IP fails closed. IPs are normalised and stored only as domain-separated HMAC rate keys. Loopback development can use HTTP and a loopback rate identity when no trusted header is configured. No environment values are logged.

All operations use POST with exact JSON shapes, no query strings, canonical Origin and no cross-site Fetch Metadata. Bodies are limited to 8 KiB/4096 chunks with a five-second read bound; requests have a 45-second response deadline and production database/auth fetches have eight-second bounds. Cancellation checks prevent subsequent work and late cookie attachment, but cannot promise rollback of a server mutation already dispatched. Responses, including errors, use private/no-store, no-referrer and nosniff. GET and other methods do not mutate anything.

Durable 016 counters allow 120 reads, 60 writes and 30 redemptions per minute per rate identity. Every accepted request first charges the trusted IP; authenticated host work then charges its verified account separately. The table is capped at 10,000 identities, with at most 100 expired rows reclaimed during new-key admission. Saturation refuses admission instead of growing indefinitely. Rate denial returns bounded `Retry-After` (1–60 seconds). This is not a replacement for deployment request-size, connection or denial-of-service protection.

## Route contract

`POST /api/events`:

- `{operation:"capabilities"}` returns public limits, transport version and readiness. It never exposes deployment usage or secrets. Upload/download availability remains false for this tranche.
- `{operation:"create",eventId,event:{title,timezone,startsAt,closesAt,expiresAt,maxGuests,maxContributions,maxBytes}}` requires host bearer authentication. Event UUID/payload are stable retries; no caller actor is accepted. Timestamp inputs require valid civil components and an explicit offset; timezone must be IANA. SQL owns lifecycle, quota and immutable retry decisions.

`POST /api/events/{eventId}` requires authenticated Supabase `getUser` through the request's bearer token and public-key client. Service identity never comes from JSON, a guest cookie or unverified JWT decoding.

- `dashboard`, with optional UUID `after` and `limit` 1–25, returns allowlisted event fields, receipt summaries and usage. It omits owner/internal fingerprints, token hashes and worker/provider fields.
- `manage` with exact `action` and `body`: update, open/pause/close/delete, revoke_guest, invite_moderator/accept_moderator/revoke_moderator, publication and remove_submission. SQL retains owner/moderator separation; removing a moderator does not transfer ownership.
- `issue` takes requestId, kind `invite|gallery|display`, expiresAt and rotate. Rotation is allowed only for invites. Server-derived secrets are returned once per explicit response, with actual bounded expiry and `fragmentOnly:true`. The same exact retry reproduces its token, without creating or rotating again. At most 64 retained invite/read issuance records exist per event, including revoked ones; saturation preserves provenance. A revoked old request cannot revive its token.
- `revokeToken` takes the raw issued read token, hashes it server-side and revokes only within this event. No caller hash or SQL action is forwarded unchecked.

`POST /api/events/{eventId}/guest` needs no account:

- `redeem` takes inviteToken and a private 32-byte base64url nonce generated by the browser. Retain the nonce only to retry this exact exchange; do not publish it. Server HMAC derives a stable guest UUID/contribution token from event, invite and nonce. Only hashes reach SQL. A lost response can be retried without consuming another guest slot while the invite remains valid. Revoked/expired invites cannot restore access.
- `session` checks the current contribution cookie against the exact event, token kind, guest revocation and expiry.
- `reserve` takes requestId, submissionId and three explicit consent booleans (`submission`, `gallery`, `wall`). Submission must be true; neither publication destination defaults to true. This tranche binds only the current guest as contributor. Multi-person postcard transfer remains P8 work. The response contains its private receipt and portable receiptToken before any upload, never a Storage path or upload authorisation. Receipt identity is deterministic across exact retries.
- `consent` takes submissionId and the three booleans; SQL checks the current contributor. `finalise` takes submissionId and only enqueues through the existing gate. It returns a receipt, never a worker lease, and cannot finalise an unuploaded reservation. Provider endpoints are not part of this tranche.

`POST /api/events/{eventId}/receipts/{submissionId}`:

- `exchange` takes a receipt token, validates exact event/submission/kind/expiry/revocation, reads its receipt and installs only a receipt cookie.
- `read` uses that cookie and repeats current permission checks. Contribution, gallery and display tokens cannot substitute for receipt authority. A deleted receipt can report deletion while every media read remains independently denied.

## Browser capability handling

Future redemption UI must take secrets from the URL fragment, remove the fragment with `history.replaceState` before requests/analytics, then explicitly POST to the endpoint. Never put secrets in a query, path, referrer, analytics event or server log. This tranche supplies the HTTP exchange, not a browser page that has already performed that cleanup. The returned portable receipt secret is a bearer capability: forwarding its eventual receipt link grants its private receipt access. No service key is sent to the browser.

Production uses exactly two fixed cookies: `__Host-pb-event-contribute` and `__Host-pb-event-receipt`. Both use Path=/, no Domain, HttpOnly, SameSite=Strict and Secure; the __Host prefix prevents sibling-domain cookie injection. Cookies expire no later than the verified server token, capped at 30 days. Each kind has one active browser slot. Exchanging another event or receipt explicitly replaces that slot; it does not revoke prior server grants. Keep a private portable receipt link to revisit earlier receipts. The local HTTP variant has unprefixed names and Path=/api/events. Duplicate cookie names are rejected. Cookie presence alone never establishes event or submission scope.

The secret must stay stable while pending issuance/redemption/reservation retries exist. Rotating it changes derived retry identities; existing issued hashes remain authoritative, but recovery needs an explicit operational plan. This implementation does not silently rotate keys or migrate outstanding retries.

## Validation and remaining gates

Focused tests use actual handler/store code with injected RPCs and synthetic tokens. Disposable PostgreSQL exercises direct-role denial, token kind/event/submission isolation, expiry/revocation, invite rotation preserving established sessions, exact issuance retry, concurrent last-slot rate/metadata ceilings, bounded housekeeping and empty/populated reruns. Storage tables are metadata fixtures. No native cookie/fragment page, hosted authentication, proxy-header trust, Storage token, provider byte transfer or live guest/host workflow is claimed.

On 23/09/2026, 18 focused event HTTP/store tests, whole-project TypeScript and scoped ESLint passed. `node database/tests/run-event-transport.mjs` passed the full disposable 016 suite, including six competing connections at the final rate/issuance slot, expiry rejection and populated rerun; its uniquely named database was removed. The first TypeScript pass found the root route exposing an incompatible optional string argument; a native Request-only wrapper corrected it before the passing rerun.
