# Durable ritual foundation

Forward migration `009_v2_rituals.sql` extends `pb_photo_dates`; it does not create a second scheduler. It depends on the existing couple/photo-date schema and the project actor-rate RPC from 002. It neither replaces the activity capability function nor requires activity migration 006. `pb_ritual_capabilities` reports version 1, a 20-date couple limit, 20-row page limit, 30-second proof window and `deliveryVersion:0`.

`createRitualStore` is disabled unless `PB_MEMORIES_ENABLED=true`, service configuration is valid, fresh token authentication succeeds and the exact ritual capability matches. Its public methods are `list`, `create`, `upgrade`, `edit`, `pause`, `resume`, `delete` and `setChannels`. Every operation takes the original `coupleId`; mutation identity is the authenticated actor, never a supplied recipient. Reads/writes use the existing durable actor rate gate. Provider operations and HTTP/UI integrations are not included.

## Schedule identity

`RitualDefinition` contains version, anchor date, wall-clock time, explicit IANA zone, once/weekly/monthly/yearly cadence, interval 1–12, explicit clamp/skip, gap and fold policies, and a nullable exact one-off instant. Daily recurrence is deliberately excluded. One-offs preserve their seconds and exact instant; their civil date/minute must match the chosen zone. No old timezone is inferred.

An anchor remains fixed while recurrence advances within a revision. Explicit edit may replace anchor/time/zone/policies and increments the revision. Pause, resume, deletion and recipient preference changes also increment it, invalidating future claims for the prior revision. There is no generation reset. Existing historical delivery rows are preserved; their legacy group-email key must never count as a future per-recipient ritual delivery.

The trusted service obtains the current database instant from `pb_ritual_context`, runs `computeRitualProof` using the existing bounded `ritual-schedule` primitive, then submits its next occurrence to a service-only mutation. SQL validates the strict schedule/proof shape, known database zone, short proof lifetime, future UTC instant, civil-zone correspondence and revision under the original couple/date locks. SQL does not independently reproduce the JavaScript DST resolver. Only the authenticated server adapter may supply this proof; a future HTTP endpoint must accept the public definition, never a caller proof/cursor. An expired proof fails with `schedule_changed`, without an automatic stale write. Resume selects a future occurrence from the original anchor, without backlog. An exhausted/elapsed one-off remains disabled.

Create retains an immutable initial request identity separate from the current schedule. Exact UUID retries return the existing row, even when the computed next proof has changed or expired. Changed initial payloads and deleted-ID reuse conflict. Explicit upgrade checks the old scheduled instant to reject a concurrent legacy worker advance, clears legacy active atomically, and creates revision 1. It requires a caller-confirmed definition and future occurrence.

## Scope, compatibility and consent

All insert paths, including the old direct client insert, lock the couple row and enforce at most 20 non-deleted dates. Existing over-limit rows remain listable through pagination. Creator/couple/date identity is immutable; insertions into someone else's couple fail even if an old permissive policy would accept the creator ID. Service RPC execution permissions and an actual service database role check protect actor-bound operations. A JWT-claim string alone does not grant RPC execution.

Versioned rows always have legacy `active=false`. A separate enabled flag and partial due index are reserved for the upgraded worker. Restrictive RLS hides versioned rows from legacy clients, and a trigger rejects direct versioned-column forgery/reset, direct activation and old service-worker updates. New protected recipient preferences default to both channels off. A recipient can change only their own preferences; the creator cannot grant their partner's consent. Original recipient IDs are frozen at create/upgrade and intersected with current exact-couple membership. Replacing a couple member or re-pairing grants no old ritual access. Unpairing cascades the dates and preferences and makes the original scope unavailable.

Service deletion of either a versioned ritual or a genuinely legacy row is a creator-only revision-fenced tombstone, not an early removal of delivery identity. It clears active/enabled state and frees its non-deleted date slot, while preventing UUID recreation. Legacy rows require an explicit upgrade before using versioned pause/resume, so those actions never infer an old timezone. Tombstone/occurrence compaction requires the future worker's terminal-generation contract; this tranche does not silently delete them.

## Deliberate remaining gates

`deliveryVersion:0` means migration 009 alone has no versioned reminder claim, send, completion or retry integration. Forward migration 010 and the existing scheduler now provide that separate capability as described in [P6_RITUAL_DELIVERY.md](P6_RITUAL_DELIVERY.md). Management accepts either delivery version; lack of worker support does not block reads or edits. Do not select `ritual_enabled` rows with the legacy worker. The legacy worker remains restricted to `active=true` rows. Hosted activation and real provider evidence remain pending.

Local verification covers strict definitions, exact one-offs, database-time recurrence, channel/identity boundaries, malformed projections, rate failures, old-schema failure, disposable SQL reruns, a populated over-limit legacy migration, concurrent cap/CAS races, direct-write attacks, explicit upgrade/edit and unpair/member replacement. These checks do not validate hosted delivery, email/push providers, HTTP or rendered UI. No hosted migration or flags were changed.
