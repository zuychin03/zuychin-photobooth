# P6 private project foundation

This document specifies the 002 scope foundation, not the complete P6 feature or a deployed migration. The subsequent [HTTP and maintenance integration](P6_PROJECT_HTTP.md) and [browser client](P6_CLOUD_CLIENT.md) now consume these contracts. The `/projects/cloud` library is integrated behind the existing disabled server capability. No hosted schema or cloud write activation has occurred. References below to later integration describe the boundary of this database layer.

## Scope and authority

`pb_projects` represents an explicit personal or friend scope. The creator is accepted immediately; a friend must accept an invitation as their authenticated user. There are at most four lifetime membership identities, including the owner. Revoked membership cannot be silently reactivated or replaced in the same scope. Create a new project for a changed group. Personal scopes cannot invite friends. Couple pairing, unpairing and re-pairing confer no project access.

`createProjectStore(accessToken)` verifies the token with `auth.getUser`, captures that actor ID and never accepts a body-supplied actor. Every SQL action independently checks service authority and membership. Tables have RLS enabled and direct table grants removed, including service-role table grants. Only explicit RPCs are granted to `service_role`. Administrative SQL can still bypass these protections and must remain trusted.

## HTTP rate gate and project discovery

The authenticated project store additionally requires `apiVersion: 1` in schema capabilities. Missing or older capabilities fail closed. Migration 004 preserves this marker when replacing the project capability function.

Before each public HTTP operation, its handler must call `store.rate("read" | "write" | "upload")`. Reads include listing, viewing, status and resolving a private read URL; writes include project/member/reservation/finalisation/delete actions; upload is for signed-upload mint requests. `pb_project_rate` binds the actor verified by `getUser`, locks one durable row for that actor and independently limits reads to 120, writes to 30 and upload mints to 12 per fixed minute. The three counters reset together when the database minute advances. This deliberately allows a boundary burst across two adjacent minutes; it is not a sliding-window limiter. Rows do not grow with requests or timestamps, and an actor cannot allocate records for arbitrary identities through the public store. Direct table access and client RPC execution are denied. Exhaustion produces `ProjectServerError("rate_limited", 429, retryAfterSeconds)` with a bounded 1–60 second delay for the HTTP Retry-After header. Denied requests do not increment counters beyond their ceiling. This actor gate does not replace edge protection for unauthenticated traffic or bound total account creation.

`store.list(after?, limit?)` exposes authorised discovery without requiring users to know a project UUID. It returns `{ projects, nextCursor }`, ordered by immutable UUID ascending, with a default page of 20 and a maximum of 50. `nextCursor` is the final returned UUID only when another visible row exists. The SQL query applies current actor membership and active project status on every page; cursor possession conveys no authority. Membership changes between requests can change the visible collection, so this is not a snapshot export.

Every list item contains only `id`, `ownerId`, `kind`, `title`, `createdAt` and `membership: "accepted" | "invited"`. Pending invitations reveal this minimal discovery metadata and still cannot call the full project view, resolve assets or read another member's private submissions. Revoked memberships, deleted projects and projects connected only through a couple relationship are omitted. Accepting an invitation continues to use the existing actor-bound membership RPC. Listing includes no asset identifiers, paths, captions, recipes, member roster or capability tokens.

The rate and list RPCs are service-only primitives. The store keeps them explicit rather than silently charging internal worker operations; public handlers must invoke the appropriate rate gate before forwarding an operation. No public activation is performed by this migration.

The private `photobooth-projects-v2` bucket has no direct client access. A restrictive policy denies this bucket even when another permissive Storage policy exists. The service resolver checks the current accepted membership and the asset gate and returns a private descriptor, not a public URL. A future endpoint must mint a read URL immediately after this check, with at most 300 seconds lifetime and private/no-store responses. Membership revocation blocks subsequent resolutions; already issued URLs and downloaded copies cannot be recalled. Descriptors must never be cached as proof of current authorisation.

`pb_project_view` omits inaccessible protected assets entirely, including their identifiers and metadata. Ordinary project metadata and membership do not contain photo recipes or protected captions. `pb_saved_templates` is a reserved, RLS-denied table; no cloud template write API exists yet. Cloud source manifests must later use the authoritative project parser and migration path, not assume one fixed local schema version.

## Protected challenge assets

Assets have the closed protection enum `none | challenge`, plus a required challenge UUID for the latter. Unknown protection fails. Migration 002 refuses all new challenge reservations through `pb_project_protection_write`. Its protected read gate grants only the accepted asset author access; even the project owner has no generic override. There is no client-controlled revealed boolean and no permissive membership policy to bypass this gate.

Migration 004 must replace the write/read gates with authoritative challenge checks, including scope, accepted frozen roster, consent, current lifecycle and an atomic reveal decision. It must also update capability reporting. Apply migrations in order; do not replay an older migration after later migrations have replaced its functions. Until 004 exists, challenge writes remain unavailable. A trusted migration/test may insert a protected row to prove author-only reads; that is not an available client path.

## Reservations and accounting

Both `PB_CLOUD_PROJECTS_ENABLED=true` and an explicit positive database project deployment allocation are required. Default allocation is zero. Capability checks also require the private bucket and the expected protocol limits. The service URL must be HTTPS or local loopback HTTP. Each network request has a 10-second fetch abort; this is not a hard total execution deadline.

Project creation atomically reserves its full configured maximum, from 10 MiB (one upload ceiling) to 64 MiB, against `pb_project_configuration.deployment_bytes`. This allocation is independent of the event allocation in 005. An operator must partition real provider headroom across projects, events, legacy media and other uses; setting both budgets does not create extra capacity. No inferred free-plan allowance is used.

Each project holds at most 24 charged files and 48 Mi pixels. Photos are at most 10 MiB, 4096 pixels per edge and 12 Mi pixels each. Decorations are at most eight PNGs, 4 MiB and 2048 pixels per edge each. All sizes are bounded before allocation. An asset records its expected encoded byte count, decoded dimensions, MIME and SHA-256, but initially holds the full 10 MiB bucket upload ceiling. Signed upload tokens do not enforce a smaller claimed size. Finalisation shrinks the charge to verified bytes after the object becomes immutable. Thus concurrent uploads require temporary headroom, even for small decorations. Failed or expired assets retain the ceiling until confirmed cleanup; ready deleted assets retain their verified charge. UUID tombstones and immutable request fingerprints prevent request reuse or changed-payload retries from rebinding an original.

Reservations allow ten minutes for finalisation. Authorising an upload opens one 60-second mint window, records the maximum two-hour signed upload validity after that window, and delays cleanup a further five minutes. Exact server-generated paths are `project UUID / author UUID / asset UUID`, without filenames or user-supplied paths. Uploads must use no overwrite. The Storage metadata trigger rejects unreserved paths, expired reservations, removed authors, moved objects and writes to ready/deleted assets, and challenge writes after access loss. Existing object metadata cannot be updated, even while verification is pending, so verification cannot race an overwrite. Client deletion is unavailable.

The server adapter's `authoriseUpload(projectId, assetId)` returns a typed, allowlisted envelope only after verifying the exact requested project/asset and authenticated author path, private bucket, bounded bytes, `overwrite=false`, a still-open mint window, the exact two-hour upload deadline and five-minute cleanup margin. Unexpected, denied or malformed responses cannot reach a future privileged mint operation. The mint caller must still check the deadline immediately before sending the provider request. Create the store per authenticated request; do not cache it across sessions.

## Durable original finalisation

The user-bound adapter exposes `enqueueFinalisation(assetId)` and `finalisationStatus(assetId)`. Both bind the verified author. Enqueue checks accepted membership, current challenge permission, an authorised upload and the unchanged ten-minute reservation deadline. The asset UUID identifies one durable job; repeated enqueue cannot reset attempts, failure or deadlines. Ready originals return their existing completed status.

`createProjectFinalisationStore` is a separate service-only adapter. It also exposes bounded `sweep(limit)`, `claimCleanup()` and `finishCleanup(claim, confirmedAbsent)` for the dedicated project maintenance worker. `claim()` returns at most one strictly validated descriptor, with original reservation metadata, exact private path, owner, protection and token lease. The SQL scanner considers at most 25 due records and locks project, asset, then job; competing workers skip held locks. The lease lasts at most 120 seconds and never past the reservation deadline. Metadata is not accepted from the HTTP caller.

`finish(claim, outcome)` accepts `verified`, `retry` or `reject`. Verified completion checks the current lease and rechecks accepted membership, challenge permission, lifecycle, deadline, exact reservation metadata and Storage metadata size. It then atomically marks the original ready and the job complete. The old `pb_project_finalise` helper is private, including to direct service-role callers; it cannot bypass the lease entrypoint. Decoder failure, revoked access and expired reservations do not make an object ready or release its charge.

A provider failure retries after five seconds, at most eight claims. Explicit rejection is terminal. An eighth crashed worker becomes terminal after its lease expires; enqueue cannot reset it. Failed reservations remain charged and the existing expiry sweep queues cleanup at the original safety deadline. A lost successful response is recovered from status or repeated enqueue, not by trusting an expired completion token. Operators must reconcile terminal failures before any manual repair.

The adapter returns typed allowlisted project, member, reservation, view and job projections. Public job status never exposes worker lease tokens or Storage paths. Capability `finalisationVersion=1` is required, including after migration 004 replaces project capability reporting. No API or Storage worker is activated here. The separately tested `verifyProjectOriginal` primitive provides actual native verification, but a future worker still must stream and bound downloaded bytes before calling it, and then pass only its trusted result. SQL metadata alone cannot prove decoding.

## Cleanup

Delete immediately removes read access and queues a separate project cleanup record. Expiry sweep handles at most 25 reservations per call. Cleanup claims one record with a 120-second token lease. A worker must check its lease and the immutable descriptor before external deletion, then pass a confirmed-absence result. Finalisation checks the current lease, inactive asset, upload safety deadline and absent Storage metadata. Failed deletion keeps charges. A stale lease cannot release quota. Project allocation is released only after project deletion and confirmed cleanup of all charged assets, or immediately for an empty deleted project.

These functions are separate from legacy strip/relay workers. They do not automatically archive project media to Cloudinary. Worker implementation, recovery UI, storage-provider absence verification and provider-token tests remain future integration work.

Cleanup has an eight-claim ceiling. False or unknown absence results keep all charges; the eighth failure becomes terminal `failed`. An eighth worker crash becomes terminal only after its live lease expires, in a bounded scan during subsequent claims. Terminal records are not automatically retried. They retain the asset path, attempts, status, and unconfirmed accounting for operator investigation. Recovery must first establish that no old worker remains active, reconcile actual provider objects and upload deadlines, then explicitly repair/requeue the same record under service authority. Do not clear quota or mark absence merely to unblock a project. There is no public retry/reset API in this foundation.

## Verification

`tests/cloud-project.test.ts` exercises default/config/auth failures before RPCs, actor binding, strict image/protection payloads and resolver descriptor validation. `node database/tests/run-projects.mjs` creates and removes a disposable database in the task-owned local PostgreSQL container. It tests empty and populated migration reruns, coexistence with legacy/P1, direct grants, invitation and revocation, no couple inheritance, protected-owner denial, a permissive-policy bypass attempt, concurrent project and asset allocations, exclusive cleanup leases, deletion accounting and late upload rejection. Finalisation regressions exercise concurrent enqueue/claims, stale lease rejection, no-overwrite before/after ready, rejected decoder assertions, successful charge reduction, reservation expiry, revocation and the eight-attempt terminal limit. The challenge harness uses the same fenced path and verifies cancelled/expired/withdrawn/revoked uploads cannot commit.

The rate/discovery additions passed 12 focused TypeScript tests, focused TypeScript compilation and ESLint, plus the disposable PostgreSQL harness. SQL checks include eight competing requests for two remaining upload-rate slots, independent actor/scope counters, fixed-row reset, client grant denial, invitation-only projection, multi-page cursor continuation and omission after revocation/deletion. The populated migration rerun passed with the new rate rows retained.

The local database harness uses Storage metadata fixtures. It does not exercise hosted SQL, Storage token minting, actual upload bytes, codec verification, signed URL expiry or real devices. Those checks remain required before enabling cloud projects.
