# Cloud editable design contract

Migration `012_v2_project_designs.sql` is a local candidate, not a hosted activation. `PB_CLOUD_PROJECTS_ENABLED` remains disabled by default. Existing original operations retain their current capability contract. Design operations additionally require `pb_project_design_capabilities().designVersion = 1`, `retirementVersion = 1` and exact limits. A pre-retirement schema fails these operations closed.

`lib/projects/cloud-design.ts` validates a version-1 envelope containing the current portable `PhotoProject`, one immutable binding per inventory media item and descriptive participant/uploader bindings. This includes retired media and originals referenced by undo history, templates, companions and Then-and-now. The existing project parser validates every media reference and editor field. Device camera IDs and account-local scope are excluded. A participant/uploader mapping is not proof of the person depicted or consent.

Limits are 64 KiB for the project JSON, 80 KiB for the complete snapshot, 84 KiB for its HTTP request, 24 inventory bindings and four participants. SQL allows 96 KiB of expanded `jsonb::text` for its added whitespace. The service is the trusted complete-schema validator; SQL independently enforces membership, ready asset metadata, kind, immutable owner/hash, source inventory completeness and the current protection gate. Arbitrary direct service-role writes are outside the client trust boundary. All tables and helper functions are revoked from client roles; canonical RPCs are service-only.

The cloud project owner alone commits a canonical snapshot. Accepted members may read only when every bound source remains ready, belongs to the exact project, has an accepted uploader and passes `pb_project_protection_read` for that reader. This check covers the entire retained inventory on both current and previous reads. Project ownership never bypasses the source protection gate. A protected owner-only source therefore makes the whole snapshot unavailable to an unrevealed peer; the endpoint does not return a redacted caption, design, source list or partial checkpoint. Withdrawal/revocation/deletion may make a retained snapshot unreadable. A downloaded copy cannot be revoked.

Each project keeps exactly one current and one previous checkpoint. Saving uses a separate cloud revision, beginning at zero with `expectedRevision: null`. It never treats local `PhotoProject.revision` as cloud concurrency authority. The project lock serialises saves, membership changes and normal asset deletion. The database computes SHA-256 over its canonical JSONB representation, not a caller-supplied hash. Exact request ID, expected revision and content retries return the original receipt; changed retries fail. Local project identity, creation time, capture timezone and a previously set capture time cannot be rebound. Source-order edits do not delete originals or release their storage charges.

An explicit repair may omit unavailable inventory and participant entries from the new current snapshot. The complete project validator must first remove every corresponding current, template and undo-history reference. SQL validates authority for every source that remains or is added. This does not bypass protection for the old snapshot: the previous checkpoint remains wholly unreadable if any of its sources are inaccessible. The service never returns a redacted old recipe for reconstruction.

`binding_ledger` and `participant_ledger` retain immutable lifetime identities in the same design row. The limits are 24 distinct lifetime bindings and four distinct lifetime participants, not a replenished allowance after retirement. A removed media ID cannot bind another asset, a removed asset ID cannot acquire another media ID, and a participant ID cannot switch uploader. A retired identity can return only with its exact original binding and current authority. Ledgers have independent JSONB array/count/byte constraints. Populated upgrades initialise only null ledgers from the old current snapshot, which contained every previous identity under the former append-only rule. Migration reruns preserve already populated ledgers even when the current snapshot omits those entries. Omitting an original never frees its storage charge or deletes its bytes.

The owner-only `head` operation returns only the current receipt, including its cloud revision, or null. It remains usable when a retained snapshot's source access is lost, allowing a repair from a separately held, authorised local copy under CAS. It exposes no snapshot, participants, media inventory, caption, path or URL. A new device without that local copy cannot reconstruct inaccessible content from the receipt; it must use an existing accessible checkpoint or recover a local backup. Head is not permission to read any source.

There are at most 100 immutable receipt rows per project, each containing only request identity, expected revision, hash and the result receipt. Reaching that ceiling rejects further saves with `capacity`; it never evicts IDs and lets an old retry become a new write. Reads, exact retries and save-status recovery remain available. A future increase or receipt retirement protocol requires an explicit migration. Re-saving every keystroke is not the intended integration: the following browser tranche will implement explicit durable save operations.

`reference` is now an explicit cloud original kind using photo image limits and native byte verification. It is always unprotected and cannot be uploaded or submitted as a protected challenge photo. Reference reservations require the new capability before a write; photo/decoration requests still work on compatible older SQL. Existing activity triggers deliberately record `photo` only, so reference imports do not become new capture activities. No existing reservation, quota, cleanup or provider-read contracts change.

The separate authenticated same-origin endpoint `/api/projects/design` accepts only:

- `capabilities`
- `head` with `projectId`, restricted to the current accepted owner
- `read` with `projectId` and `checkpoint: current | previous`
- `save` with `projectId`, `requestId`, `expectedRevision` and `snapshot`
- `status` with `projectId` and `requestId`

All responses use private/no-store and no-referrer headers. Requests have byte, chunk and five-second body limits. Provider/auth/RPC fetches retain the existing ten-second per-fetch bounds, rather than claiming a hard ten-second total request deadline. The existing durable actor rate gate runs before read/save/status work. No signed URLs or Storage paths are persisted in snapshots or receipts. Status is owner-only and reveals only the receipt, not old snapshot content.

`CloudProjectClient` adds `designCapabilities(signal?)`, `designHead(projectId, signal?)`, `readDesign(projectId, checkpoint?, signal?)`, `saveDesign(projectId, expectedRevision, requestId, snapshot, signal?)` and `designSaveStatus(projectId, requestId, signal?)`. Each uses the existing account/epoch fence and bounded transport. Future `PhotoProject` schemas returned by a later compatible service stay unsupported and exportable as raw snapshot JSON; this service rejects new unsupported writes. Source access is checked before any snapshot, including future raw data, leaves SQL.

The save/reopen coordinator, durable multi-asset save journal, UI and hosted validation are intentionally not implemented in this tranche. They must flush local edits, preserve upload bindings and exact request IDs before network work, wait for verified originals, and distinguish device save from cloud save. Opening must download through fresh authorised integrity reads and persist a local copy before navigation.

Local verification: `node --import tsx --test tests/cloud-design.test.ts tests/cloud-project.test.ts tests/cloud-client.test.ts tests/image-finalise.test.ts`; disposable PostgreSQL `node --import tsx database/tests/run-project-designs.mjs`. The latter uses a unique database and exercises permission, CAS/retry/cap races, protected inventory access, revocation, reference finalisation and migration reruns. Neither sends provider requests or applies hosted SQL.

The expanded disposable PostgreSQL suite passed populated ledger backfill, repeated migration after retirement, concurrent deletion repair, revocation repair, owner-only head while snapshot access fails, protected previous-checkpoint refusal, unchanged storage charges, exact authorised identity return, media/asset/participant rebinding refusal, lifetime 24/4 limits and the unchanged 100-receipt ceiling. The fixture also proves revoked sources cannot be reintroduced. Its unique test database was removed on completion. No hosted database or provider operation was performed.

Export-settings compatibility (23/09/2026): migration 028 follows the numbered migration chain and extends design writes to manifest schemas 3 and 4. It adds `exportSettingsVersion:1`; the service refuses schema-4 saves without this marker while preserving schema-3 retry/read operations. No snapshot, ledger or existing receipt is rewritten. New schema-4 snapshots carry validated per-project still/print settings, and a prior reader preserves them as future read-only backups. The focused disposable design harness now applies 012 followed by 028 on every rerun and verifies old exact-request replay after a schema-4 successor.
