# Guided stories in asynchronous challenges

Migration `015_v2_challenge_stories.sql` adds a nullable, immutable creation-time StoryPlan to the existing challenge recipe. It follows 008 and preserves the existing challenge, upload, disclosure and partial-consent contracts. This is source-level integration, not hosted activation or physical-camera evidence.

Guided creation requires `storyVersion: 1` from challenge capabilities. Existing free-pose challenges and operations work without that marker. The browser and HTTP interfaces use optional `story` on `ChallengeCreate` and `ChallengeView`. An absent or null creation story normalises to omission, preserving existing request fingerprints and recipe hashes. A non-null story participates in the frozen recipe hash. Migration reruns do not rewrite old challenges, consent digests or snapshots.

StoryPlan is the existing authored catalogue reference: version 1, one of twelve deck IDs, a uint32 seed and unique relaxed step indices 0–3. Arbitrary prompts, captions, paths and credentials are rejected. SQL independently checks the same catalogue and bounds. The story's catalogue version must retain its authored semantics; changing prompts in place would alter an already-frozen story without changing its identity.

Prompt identity is `assignment.sourceIndex`, not assignment slot or list position. The union of sources must cover exactly steps 0–3. Sparse assignments remain sparse: the alternating duo gives A steps 0 and 2, and B steps 1 and 3. Existing four-person, three-shot geometry is not a four-step guided challenge; the four-shot story layout is suitable. Director ordering uses frozen members sorted by role, with the existing seed-based selection. No extra photo, retake or submission is implied by another member's prompt.

Existing version-1 creation recovery records keep their original schema. Explicitly guided creation uses record version 2, whose form contains a nullable story. Removing a story from a version-2 draft retains that record version. Pending requests retain the exact story and request ID across retry; changing a seed or relaxed step requires resolving the pending request first. Partial-proposal records remain version 1. The same account-scoped journal limits, CAS, cleanup, read-only future records and byte bounds apply.

Partial results retain projection version 1. Their digest already includes the frozen recipe hash, so a guided story is bound without exposing any new concealed source. The partial-detail integrity check understands both old hashes and story-bearing hashes. Contributor-only geometry, consent, membership checks and underlying asset read gates remain authoritative.

The isolated PostgreSQL regression exercises populated migration reruns, unchanged legacy creation and revealed partial results, sparse guided assignments, exact replay and conflicting seed, malformed story rejection, concealed source denial, guided partial disclosure and membership revocation. Storage rows in this harness are explicit metadata fixtures, not proof of a hosted provider or real camera. UI and browser receipts are recorded separately by the integration owner.
