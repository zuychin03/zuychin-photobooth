# P1 cron and reminder safeguards

Implemented locally on 23/09/2026. Hosted activation and delivery have not been tested.

Existing `/api/reminders` and `/api/retention` URLs remain. Schedulers must use `Authorization: Bearer <CRON_SECRET>` in a header. Remove `?secret=...` from configured URLs; query-string secrets are rejected even alongside a valid header. URL query credentials can remain in scheduler/access-log history, so rotate any previously used secret through the deployment's normal secret management. Responses are private/no-store and do not return configuration values or provider errors.

All maintenance routes use the shared `authorizeCron` boundary before creating privileged clients. Missing/blank CRON_SECRET, service-role key or valid Supabase origin returns 503; invalid authentication returns 401. Supabase URLs require HTTPS except local loopback HTTP for disposable local databases. Reminder delivery additionally requires `PB_PUBLIC_ORIGIN` to be an exact HTTPS origin without credentials, path, query or fragment. Incoming Host and forwarded headers never form reminder links. User titles are HTML-escaped.

Apply reviewed migration 001 to a disposable environment before enabling the updated scheduler. The reminder route requires the service-only `pb_acquire_job_lease`, `pb_release_job_lease`, `pb_record_reminder_delivery` RPCs and `pb_reminder_deliveries` table. Missing schema fails with 503 before delivery. No hosted SQL was applied by this work.

Each reminder run acquires job `reminders`, processes at most five due dates ordered by schedule, and renews its 900-second token lease before each date. A competing active run returns 409. The scheduler should regard 409 as a collision to retry later. Each Supabase/email/push request has a ten-second abort deadline. Push fanout is bounded at 20 subscriptions per date; exceeding this leaves the date due and returns 503 for operator attention. These bounds deliberately favour safe retries over large batches; review scheduler capacity before launch.

Successful email and each successful push subscription receive separate durable delivery checkpoints. Schedule updates match the original active occurrence. Provider errors (including resolved email error payloads), database errors, no reachable recipient, partial push failures and failed lease release return 503. Failed dates stay due. Retries skip checkpointed channels; expired push subscriptions are removed with database errors checked. An email uses a stable occurrence idempotency key, and push uses a stable collapse topic. Concurrent runs and checkpointed retries are covered by local fixtures.

Delivery is not exactly once: a crash after provider acceptance but before its database checkpoint can still repeat a push; email deduplication is limited to the provider's window and identical payload. Resend retains idempotency keys for 24 hours, so a changed title/recipient can produce a payload-conflict error during that window. See [Resend's idempotency contract](https://resend.com/blog/engineering-idempotency-keys). Do not claim provider delivery, device receipt or crash-proof exactly-once behaviour from local tests.

Validation uses the actual handler with injected adapters and the production HTTP adapter with mocked fetch. It covers fail-closed config/auth with zero adapter creation, canonical origin, HTML escaping, resolved provider/database errors, deterministic retry keys, schedule-update failure, partial push retry and competing leases. Fixtures make no hosted database requests and send no emails or pushes. Real service-only RPC permissions/concurrency, real scheduler headers, provider delivery and device notifications remain activation gates.
