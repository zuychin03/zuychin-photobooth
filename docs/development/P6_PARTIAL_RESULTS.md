# Authorised partial challenge results

Migration 008 adds discovery and export metadata over the immutable partial consent protocol from 004. Apply the numbered dependencies in order, including project 002, challenge 004 and discovery 007. It preserves the existing minimal partial view and all propose/consent/commit request and response shapes. Existing feature flags remain disabled. No UI, renderer, media worker, scheduler or hosted configuration is activated by this tranche.

The additive schema capabilities are `partialVersion:1, partialListMaximum:20` and `ownUploadsVersion:1, uploadListMaximum:20`. Existing challenge version 2, recipe version 1 and discovery markers remain unchanged. The new operations require their marker; older compatible servers can still serve the original operations. All three RPCs require service role, fixed search_path and the verified actor supplied by the server adapter. Direct anonymous/authenticated calls and direct table access remain denied.

`listUploads(challengeId, after?, limit?, signal?)` returns `{version:1,uploads:CloudProjectAsset[],nextCursor}` with UUID keyset pages of at most 20. It discovers only the actor's own verified ready photo originals protected by this exact challenge, independently of browser upload tracking. Current accepted project membership and membership in the immutable challenge roster are required. A valid draft or cancelled-unopened challenge returns an empty list; frozen_at marks opened contributions and is not a discovery prerequisite. Legacy challenges without a design return update_required. Other contributors, other challenges, ordinary originals and unverified/deleted assets are excluded. Own originals remain recoverable after submission, cancellation, expiry or personal withdrawal while project membership remains accepted, matching the existing author read permission. This endpoint neither reveals another person's originals nor reopens uploads/submissions. It allows the UI to recover an unsubmitted original after safe ready-journal pruning or on another browser. Each returned asset still needs a fresh authorised cloud read to obtain bytes.

`listPartials(challengeId, after?, limit?)` returns `{version:1, partials, nextCursor}` in UUID keyset order, maximum 20. Only the proposal's author or an included contributor can discover it, and the actor must still be an accepted member of that challenge and active project. Other project members, coupled accounts and excluded non-proposers gain no access. Each summary has id, challengeId, projectId, digest, status, createdAt, revealedAt, accessLost, actorIncluded, actorConsent and contributors. Each contributor has userId, role, consent (null/true/false) and status (available/access_lost). No source IDs, request IDs, caption, design, path or URL is returned by listing. These are consent summaries, not previews of concealed photos.

`partialDetail(partialId, digest)` returns `{version:1, ...summary, result}`. An incorrect digest is denied. Pending, rejected, inaccessible and excluded-proposer results are null. Legacy challenges without frozen design return only an explicit unsupported identity projection; they cannot expose or reconstruct a result.

An available revealed result contains `{projectionVersion:1, recipeHash, design, sources}`. Each source is exactly `{userId,role,sourceIndex,assetId}`. Only included recipients receive it, after all included contributors' consent is true, current project/challenge membership holds, originals/decorations remain available, the saved snapshot equals the current immutable source mapping, the partial digest matches its stored snapshot and the original recipe hash matches the frozen design/roster/assignments. The existing Storage read gate is also checked for each source. The project/challenge/partial share locks serialize this projection with project deletion, membership changes, source deletion and consent/withdrawal mutations using their existing lock order. Actual signed reads must still be resolved freshly by the cloud client; metadata is not a transferable permission.

The full challenge need not remain available. An excluded contributor's withdrawal can cancel the full challenge while a separately consented partial remains valid. Included withdrawal, consent reversal, project membership removal or included source deletion blocks that partial. The original protocol deliberately allows a new explicit partial choice after cancellation or contribution expiry; those states alone do not remove a previously authorised partial. This does not reopen uploads or reveal excluded sources.

Projection version 1 deterministically derives the partial design from the frozen original and the digest-bound contributor set. It retains canvas dimensions and retained slot geometry, removes excluded standalone slots, filters companions and promotes the first included companion when the original primary was excluded. A sole remaining source loses the split-fallback marker. Required sources and placement entries retain only included roles. Personal text layers and the default caption are removed. Shared non-personal text, decoration layers, artwork and their existing access requirements remain. Empty areas remain empty; the renderer must label the output as a partial result rather than inventing missing people or rearranging the agreed layout. Every included source index remains represented. The digest binds the original canonical recipe hash plus the exact included source snapshot; projection version 1 is deterministic and must not be reinterpreted by a future renderer without a new version.

The shared TypeScript parsers validate exact summary keys, actor consent consistency, IDs/hashes, finite arrays and cursor order. A non-null composition is rejected unless its status, recipient and all contributor gates agree. Its template is validated by the normal bounded template validator, all decoration IDs are cloud UUIDs, personal text/default captions are absent and every required role/source maps exactly once to an included member's unique asset. No additional source or excluded role is accepted. The browser uses its existing fresh-token, account/epoch, cancellation, request/response and deadline guards. Both HTTP operations charge the existing read rate once before constructing the challenge store.

The public TypeScript types are `PartialSummary`, `PartialLegacySummary`, `PartialContributor`, `PartialComposition`, `PartialDetail` and `PartialList` in challenge-contract.ts. `ChallengeStore` and `ChallengeClient` expose both methods; browser calls accept the final optional AbortSignal. POST /api/challenges accepts `listPartials` with challengeId/after?/limit? and `partialDetail` with partialId/digest. Existing `partial`, `proposePartial`, `consentPartial` and `commitPartial` remain compatible and return their minimal response, so callers should reload detail after a mutation.

Local evidence: 44 focused challenge tests passed, including eight new parser/store/HTTP/browser regressions. The disposable PostgreSQL harness (`node --import tsx database/tests/run-partial-results.mjs`) uses uniquely named pb_v2 databases and always drops them. It exercises empty and populated reruns, actual project reservation and leased finalisation metadata, pending secrecy, exact-digest denial, concurrent commits and withdrawal, excluded withdrawal, single-companion projection, the actual TypeScript design parser on SQL output, pagination, source deletion, legacy history and membership/project revocation. Own-upload cases cover ready originals before submission, cross-owner/challenge exclusion, keyset pagination, cancellation/withdrawal recovery and current project revocation. PostgreSQL auth/storage schemas are explicitly fixtures; this does not prove hosted Storage, provider bytes, physical-device memory or a deployed partial PNG flow. Renderer/UI integration and their native evidence remain separate work.
